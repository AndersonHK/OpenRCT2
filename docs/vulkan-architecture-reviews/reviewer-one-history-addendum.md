It strengthens the case for retained GPU scene data and small updates, but that is shared by both plans. It supplies no direct controlled comparison showing that geometric surfaces or constant-depth sprite components are the faster complete solution.

Plan B still offers the less expensive first attempt at using existing art unchanged. Its scalar-depth hypothesis remains unproved; the historical requirement for one ordering model across terrain, tracks, scenery and entities makes that uncertainty more urgent. Its asset construction and exact-appearance costs remain unmeasured. Existing terrain GPU work is potentially reusable by either and does not by itself select A or B.

The history changes the recommended prototype sequence and acceptance detail, rather than my vote: isolate and measure the common publication/ownership path before attributing an integrated performance result to the representation choice. Keep the shared pipeline small enough that it does not postpone the early mixed-scene visibility discriminator.

## Failures that should not be repeated

All figures below are reports from the archived journal, not independently rerun results or claims about the current checkout.

1. **Whole-world or whole-population capture as the asynchronous boundary.** The naive full-map-per-redraw experiment fell to 139.278 TPS / 36.406 FPS. Compact guest/staff capture plus a dense spatial index reached 295.455 TPS / 110.713 FPS; sparse publication reached 297.101 TPS / 75.101 FPS. Population capture alone cost about 270 microseconds. Full entity clones, compact variants and incremental payload publication also regressed; typed-page capture reached 326.606 TPS against live-state results above 336 TPS. Later frame-ahead entity/ride copying cost about 3 ms on the caller before command recording. Moving a second scan onto a worker does not remove copying, memory contention or ownership cost. [Integrated benchmark](../archive/performance-320-tps-refactor-history.md#integrated-turbo-benchmark), [later frame-ahead discussion](../archive/performance-320-tps-refactor-history.md#prong-f-shared-pathfinding-performance).

2. **Retained pixels or cached legacy paint lists as a substitute for a retained world.** Damage generated by a newer live state was not safe for an older displayed snapshot: fast vehicles left clipped fragments. An initially successful generation-change redraw passed coaster/title-transition checks but failed construction ghosts because prepared paint lists persisted. The correctness fallback rebuilt visible columns and reached 306.934 TPS / 143.952 FPS with 1.735 ms CPU draw preparation versus 0.105 ms GPU time. Persistent authoritative input/catalog data are desirable; stale derived painter output and dirty-screen repair are different mechanisms. Both plans should state this distinction. [Presentation-generation follow-up](../archive/performance-320-tps-refactor-history.md#presentation-generation-architecture-follow-up).

3. **Entity overlays or category-reserved depth ranges.** The dense-terrain checkpoint explicitly declines mixed scenes until ordering is common across categories. A terrain-only pass, unordered entity overlay or a fixed depth band per family can appear correct in isolation while failing EverythingPark overlaps. Neither a successful terrain demo nor a balloon-only path establishes a complete world compositor. [Renderer prong](../archive/performance-320-tps-refactor-history.md#prong-a-vulkan-renderer-gpu-owned-composition-and-bus-traffic).

4. **Parallelization without an ownership or locality benefit.** Classifying peeps into job queues increased their update cost from about 1.44 to 1.63 ms/tick and changed deterministic state. Bypassing the shared rating memo for independent work increased aggregate rating cost from about 0.25 to 1.47 ms/tick. Existing guest and train mutations involve shared RNG, queues, collisions, stations and ordered list visibility. Independent renderer advancement must not silently become speculative parallel simulation. The renderer project can free CPU time without changing those simulation semantics. [Integrated benchmark](../archive/performance-320-tps-refactor-history.md#integrated-turbo-benchmark), [speed/cache follow-up](../archive/performance-320-tps-refactor-history.md#speed-transition-and-long-run-cache-churn-follow-up).

5. **Optimizing one short window or a proxy metric.** A larger 524,288-entry rating cache slightly helped the hot window but regressed later windows, while a 65,536-entry trial churned. Stable route counts did not imply stable per-operation costs. Profiler leaf scopes themselves imposed measurable overhead. The 318 TPS software rows ran at about 13 FPS, whereas later Vulkan rows deliberately spent more time rendering at 144 FPS. A 3,600-tick 360.032 TPS result fell to 347.182 TPS over the longer growing-park run. Benchmarks must preserve state boundaries, measure long-run population/working-set effects, and separate clean acceptance runs from attribution runs. [Vehicle/locality history](../archive/performance-320-tps-refactor-history.md#measured-vehicle-update-follow-up), [refresh-paced checkpoint](../archive/performance-320-tps-refactor-history.md#refresh-paced-turbo-checkpoint).

The routing, fare, station and cache sections also matter: much of the historical TPS improvement came from simulation algorithms and exact cache reuse, not Vulkan. Their successes do not imply a GPU renderer alone can reach a 1,000-TPS aspiration. Their invariants—exact keys, meaningful invalidation epochs, stable publication, bounded storage, deterministic ordering and preserved integer rounding—are useful engineering examples, but their specific workload figures must not be repurposed as rendering benchmarks.

## Infrastructure to reuse, after verifying its current state

The journal documents a substantial existing foundation: the dedicated render worker and latest-frame mailbox; skip-if-busy frame admission; three fence-protected frame slots; reusable mapped upload rings; transactional atlas residency and leases; compact indexed sprite instances and retained descriptors; palette/remap/mask, transparency, weather, glyph and presentation passes; integer compute LightFX; asynchronous explicit readback; and lifecycle handling for abandoned frames and swapchain reconstruction. Build on the approved shared Vulkan service instead of rebuilding those facilities inside either candidate. [Integration and presentation boundaries](../archive/performance-320-tps-refactor-history.md#vulkan-integration-checkpoint).

The process-lifetime worker pool has independent task groups and priorities. Mutation-owned map change batches and chunked copy-on-write storage provide a useful publication pattern. Typed entity storage, stable identities and lifecycle tracking are potential source-side integration points, while snapshot declarations or dormant bulk-capture machinery are not evidence of an inexpensive live path. Dense active-map source records, GPU zoom/frame selection, stable compaction and indirect drawing can be reused where their assumptions fit; retain the full mixed-category gate. [Integrated benchmark](../archive/performance-320-tps-refactor-history.md#integrated-turbo-benchmark), [renderer prong](../archive/performance-320-tps-refactor-history.md#prong-a-vulkan-renderer-gpu-owned-composition-and-bus-traffic).

Reuse fixed-tick warm-up/measurement boundaries, actual renderer reporting, checksums and population snapshots, hidden versus visible modes, GPU fence-complete timing collection, and separate headless/integrated measurement. Extend their evidence to actual 4K dimensions and displayed pacing rather than assuming older reported FPS proves them. The archive contains evolving and superseded designs, so each reuse item requires inspection of current source; it is not a claim that all historical machinery remains active today.

## Revisions recommended for both candidate plans

- Define publication ownership concretely: simulation owners emit compact authoritative mutations during existing update/mutation work; graphics catalogs and GPU expansion derive appearance. Enumerate entity, ride, object, map-neighbor/support, weather, palette and construction-ghost dependencies. No per-frame full scan, legacy-state clone, spatial-index rebuild or CPU graphical-part expansion may be hidden in publication.
- Define a coherent generation contract covering world epoch, revision/tick, stable IDs plus reuse generations, camera capture, catalog lifetime and frame leases. Rendering pins one complete revision; a newer one replaces only a future frame. Delta coalescing must preserve changes even when intermediate revisions are skipped. Reset/load/unload and cancellation must retire old work without exposing old-world references.
- Explicitly redraw a complete visible scene from retained records on each admitted frame. Reuse immutable/resident data; do not retain dirty screen pixels or legacy prepared paint lists. Include ghosts and editor modes in the validity model from the start.
- Require bounded storage, publication/upload bytes, CPU capture/apply cost, snapshot age and contention measurements. Demonstrate simulation continuing while presentation is delayed. Define behavior under queue pressure, overflow, resize and resource failure; no dropped scene records, unbounded stale queues or implicit routine GPU wait. Migration fallback must be observable and cannot count toward a candidate's successful full-scene result.
- Expand the small mixed-scene proof with repeated park/title transitions, object or entity ID reuse, construction ghosts, changed neighboring geometry and fast movement across generation boundaries. Treat alpha holes, destination-dependent effects, deterministic ties and picking as explicit composition/identity rules.
- Keep the requested minimum of 3,000 measured ticks at actual 4K, and retain the historical 2,000-warm-up/12,000-measured-tick growing-park row as an additional capacity check. Specify hardware, refresh rate, render dimensions, camera and assets; report TPS, displayed pacing, checksum/state boundaries and headless ceiling separately. Repeated exact-state clean runs must support improvement claims; profiled worker CPU totals are not wall-clock frame times.

For **Plan A**, additionally define how original indexed art maps to surfaces without changing silhouette, sample positions, zoom art or palette semantics; distinguish physical geometry from deliberately authored occlusion depth. Count per-family/per-frame/per-rotation depth data, custom-object handling and authoring effort. Preserve every geometry/reference disagreement and classify actual corrections explicitly. A procedurally reusable depth rule is materially different from manually painting depth for every sprite.

For **Plan B**, additionally require a falsifiable specification of the scalar and the permitted local ties, including full tile-plus-subtile coordinates, component extents and parent/child grouping. Log failures by object family and overlap relation. A small decomposition must demonstrate bounded asset/runtime growth and hold across rotations and motion. Stop for review if correctness requires broad family priorities or a growing exception list; compare those same failing scenes against A's depth-bearing representation. Historical shared-painter-key plans are supporting implementation ideas, not proof that an anchor scalar works.

The archive's older suggestion to compact a CPU-stable paint order can serve a diagnostic reference or an explicitly temporary migration adapter. It must not silently become either new plan's permanent per-frame input: both candidate plans require GPU visual evaluation from authoritative state.

## Updated discriminating experiment

Keep the original mixed-art scene and compare both representations using identical catalogs, authoritative updates, palette composition and pixel sampling. Add a shared publication micro-gate that changes only the expected records, then delays presentation while checking coherent revisions and bounded cost. Measure that cost separately from A's depth creation/rasterization and B's component expansion/ordering. Preserve failures, including ghosts and epoch transitions.

If B's scalar/ties pass the bounded scene cheaply, it remains my first implementation preference. If B fails and A fixes the same overlap cases with economical depth data and unchanged art, prefer A. If both render correctly but integrated TPS falls, investigate publication, repeated CPU semantics, memory traffic and shared scheduling before concluding that the representation itself is at fault. The full history makes these failure paths foreseeable; neither a favorable prototype vote nor the archived high-TPS rows closes them.
