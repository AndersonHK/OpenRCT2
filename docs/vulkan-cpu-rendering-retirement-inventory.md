# CPU rendering retirement inventory

**Current override, build92:** ordinary viewport CPU column generation/arrangement/drawing and pixel-shift repaint are physically deleted. Native terrain publication contains raw facts, with no legacy tile vectors or eight CPU-selected images per tile. Shaders draw surfaces, cliff faces and water masks/overlays; remaining world families and auxiliary world views are omitted. Raster-only map-animation tracking and its callers are removed while real state transitions remain. Two 4K/VSync/12,000-tick runs reach 358.825–359.958 TPS and 0.0807–0.0808 ms CPU Draw. This is an incomplete architecture checkpoint, not complete parity. [Current results and deletion checklist](vulkan-snapshot-terrain-checkpoint.md). Older complete-world runtime descriptions below remain historical.

Audit date: 2026-09-23. This is a source audit and deletion map, not a claim that the replacements are complete. The Vulkan-only selection change and removal of the final production X8 construction sites are applied. Build75/run57 qualified their then-current regression scope with 855 passing tests, including 66 parity cases and clean validation. The build75-era external track-preview comparison now has 12 exact pairs and completed manual review. Fifteen saved ordered-alias cases from run58 also match and have been reviewed, but run58 aborted later in the preview test fixture. Build78 corrects that fixture; run59 completes with 866/867 passing tests because an old assertion still expected no owner mutation notification. Build79 corrects that assertion, and run60 passes all 867 tests with clean validation. Large scripted images, X8 test/oracle retirement, native-world migration and performance remain open. This source audit is supplemented by root-run evidence in the checkpoint document. [Plan B](vulkan-plan-b-retained-sprites.md) defines the target; the implementation checklist owns completion status.

## Order mandated by the owner

1. Hardwire Vulkan for graphical output and remove Software selection from the UI, configuration and command line. Missing Vulkan support must produce an explicit error for a graphical request, never choose X8. Pure simulation and asset-file operations need not create a device.
2. Retire the entire CPU **world graphics preparation and rasterization** pipeline. The ordinary viewport painter/fallback is deleted. Migrate omitted families to resident raw state and GPU visual rules, then delete each superseded family implementation and remaining consumer. Build92 removes CPU surface-image selection and native legacy tile copies. Remaining legacy profiles, bounded experimental bridges, picking and auxiliary consumers are still deletion/migration targets.
3. Retire auxiliary software raster callers and in-process world-painter oracles. Preserve reference programs as separately built, pinned artifacts. Keep necessary simulation, ownership, asset decoding and text processing distinct from the world painter.

Every rendered world frame clears and redraws the complete visible world. Resident source buffers and immutable asset catalogs are reusable; old world framebuffer pixels, dirty screen tiles and cached world raster chunks are not. Simulation advances independently of display cadence. A renderer may use the newest complete owned revision while simulation produces another, with explicit source ticks, interpolation history and lifetime epochs. It must not make simulation wait for one GPU frame per tick.

## Production layers and deletion targets

The [minimal graphical state contract](vulkan-plan-b-retained-sprites.md#minimal-graphical-state-contract) further constrains every replacement below: static tile coordinates are implicit, motion and appearance update independently, shared resident sequences drive shader image/offset selection, and camera changes update global state only. Existing complete-record peep publications are transitional, not the final bandwidth contract. Audit both producer CPU work and actual staged/uploaded bytes; reducing record size alone does not remove per-frame CPU world graphics preparation.

### Scripted image parity gaps

The translated overlapping raw self-copy difference has an implemented ordered GPU correction. It preserves within-call aliasing through mutable indexed storage and ordered compute slices on the shared service. All fifteen saved cases from run58 match explicit old-scan expectations and pass [independent manual visual inspection](vulkan-custom-image-alias-visual-review.md). Run58 nevertheless failed overall in an unrelated late-preview fixture; full regression qualification now passes in run60, with the identical reviewed alias report. This finite corpus is not fresh upstream execution or universal custom-image coverage. No pixel exception is authorized.

The current service admits at most `4 * 1024 * 1024` pixels per custom image and rejects larger targets before allocating an owned seed. Historical dimensions can exceed this bound. That explicit error is a known compatibility gap, not successful preservation or an approved size restriction. Supporting these requests requires bounded execution that preserves one callback invocation, command ordering, clipping, reads and nested side effects; replaying the callback independently for each tile is not equivalent. Large targets and sources beyond the 2048-wide/high sprite atlas remain open even when the bounded script tests pass.

Offscreen GPU rasterization is not sufficient by itself: previews and screenshots also need to stop invoking the retired CPU world painter. Their output readback is legitimate requested output, not a normal-frame GPU-to-CPU round trip. Keep one service/device owner and existing residency leases, fence retirement, error propagation and abandoned-submission recovery.

## CPU work that is not the retired world pipeline

[`SpriteAssetDecoder`](../src/openrct2/drawing/SpriteAssetDecoder.cpp) expands loaded BMP/RLE sprite data into indexed pixels plus coverage. [`GpuTextureCache`](../src/openrct2-renderer/gpu/GpuTextureCache.cpp) already calls `DecodeTrustedSpriteAsset`. Keep this as asset upload preparation; eliminate per-entity/per-frame decode misses through catalog residency. Index-zero coverage, zoom links and generation validity remain required.

Image import/export, PNG/BMP IO, palette/remap tables, font file loading, localization, text shaping and cached TTF glyph/text bitmaps are auxiliary CPU operations. [`TTF.cpp`](../src/openrct2/drawing/TTF.cpp) and `GpuTextureCache::GetOrLoadTTFTexture` illustrate cached bitmap upload. These are not a reason to keep world sprite selection on CPU. A changing world text animation must use resident glyph/text inputs and GPU phase/placement instead of uploading a freshly composed world bitmap every frame. UI layout and text changes have their own measured cost and do not require `PaintSession` world traversal.

`Drawing.Sprite.BMP.cpp`, `Drawing.Sprite.RLE.cpp`, software masking in `Drawing.Sprite.cpp`, `AVX2Drawing.cpp`, `SSE41Drawing.cpp`, and X8-only line/rectangle raster helpers become deletable after sprite-export, custom-image and oracle dependencies are severed. Confirm their remaining callers before deletion. Do not remove generic CPU feature detection: audio has unrelated AVX2 implementations. Do not remove all invalidation APIs indiscriminately: asset generation invalidation and widget state changes are different from dirty-screen world repainting.

Authoritative gameplay, pathfinding, ride physics, finance, networking, save/load and world mutation remain CPU simulation work. GPU code must consume their published facts, not re-run gameplay to guess visual state.

## State classification for the migration

“Shared/individual” describes ownership, “slow/fast” describes expected mutation frequency, and “graphical/nongraphical” describes meaning. They are independent axes. Slow never means immutable, and no category grants permission to skip the full world redraw.

| Ownership / frequency | Graphically relevant simulation facts published by CPU | Graphical data or evaluation |
|---|---|---|
| Shared, slow | Object/ride definitions, terrain materials, asset slot lifetime/generation, language/font identity. | Resident original art, zoom links, animation/component catalogs, glyph coverage, remap and blend tables. Prepare at load/mutation boundaries. GPU uses these tables to select visuals. |
| Shared, fast | Simulation tick, ride/station state shared by many vehicles, weather/time state. | Camera, rotation, zoom, interpolation fraction, palette/light state and global animation clocks. Small view/frame parameters; GPU projection, culling and visual selection. A camera move must not rebuild CPU world graphics. |
| Individual, slow | Tile/object identity, terrain/path connectivity, placement, ride ownership, colours, peep appearance/inventory changes, lifecycle add/remove. | GPU expands current raw facts and shared definitions into components. No CPU-selected image field, retained `PaintStruct` list or CPU-derived camera depth per instance. |
| Individual, fast | Peep/vehicle positions and prior positions/ticks, direction, action/state/animation counters, moving effects and mutable ride attachments. | GPU interpolation, frame/accessory selection, offsets, visibility, ordering and component emission. Stress all entities moving, not only zero-delta frames. |

Publish only facts required by a visual rule. Position, appearance colours and visible actions are graphically relevant simulation state. Exclude truly nonvisual finance, pathfinding, AI bookkeeping and similar simulation internals; when a visual rule needs information from one of these systems, publish only the small required fact, not the subsystem's working state. Never omit cross-family visual dependencies: rider colours/state, track support neighbours, path additions and scrolling signs are examples. Use stable IDs and monotonic lifetime epochs. An empty new epoch must clear old GPU residents. Catalog revision and raw state must be admitted coherently. Source deltas reduce transfer volume; they do not determine repaint regions. If publication changes every tick, measure worst-case copies/uploads and TPS while the display independently consumes complete revisions.

## Small next deletions and completion evidence

Immediate selector cleanup is complete: obsolete HardwareDisplay backend/factory/project entry, selector labels/branches, software CLI acceptance and fallback defaults are removed. Current lifecycle tests recreate Vulkan windows instead of switching renderers. No compatibility config reader selects Software. This milestone precedes the world rewrite and is reported precisely as Vulkan-only selection.

Screenshot, park-preview, track-preview, scripted-image and default dummy-factory X8 removal is applied, with each finite qualification and remaining interactive coverage recorded above. Track-preview manual review is complete for its captured build; ordered self-blit samples are exact and reviewed, with current full-suite qualification passing run60. The performance priority is direct changed-field capture and the native GPU world consumer. Remaining auxiliary deletion work includes large target/source compatibility, broader actual entry-point comparisons, replacing single-sprite export's software blitter with asset decoding, and externalizing the remaining in-process software oracles. These changes enable X8 deletion, but they do not by themselves remove CPU world preparation.

The substantial performance deletion is `CreatePreparedViewportFrame` plus every column's generate/arrange/draw path, legacy presentation clones and world command recording. Picking, LightFX and scrolling text must not retain back doors into it. Record per-family retirement and measure the final ordinary-park path: CPU world preparation time/calls, state-publication cost, transfer bytes, GPU stage time, independently advancing TPS and displayed VSync pacing at actual 3840×2160 for at least 3,000 measured ticks. Zero uploads for an unchanged fixture and passing isolated selectors are correctness evidence, not this performance result.
