**Background-policy coverage limitation (code cause established):** each ordinary image is byte-identical to its transparent-labelled counterpart at all four retained layers: PNG, indexed pixels, palette and RGBA. The 16 reviewed paths therefore contain eight distinct PNGs. Both variants have an indexed PNG `tRNS` chunk making palette index 0 transparent, and their decoded alpha is exactly 0 at index 0 and 255 elsewhere. The image viewer displays that outside background as black; alpha was checked separately from the visual appearance. These cases exercise both command invocations but do not establish distinct opaque-versus-transparent behavior. This is a coverage limitation, not a rendering exception or permission to change the frozen output.

The frozen configuration reader defaults `transparent_screenshot` to **true**, and the original input configurations omit this setting. `ApplyOptions` enables transparency if either that configuration value or `--transparent` is true. Therefore both original lanes are **default-config-transparent**; the retained name `ordinary` means only that no command switch was supplied. It does not mean an opaque viewport. All 16 original paths and bytes remain unchanged.

A legitimate existing distinction is reachable by explicitly setting `transparent_screenshot = false` in a separate config. Ordinary drawing then paints outside-map blank tiles, while `--transparent` suppresses them. Read-only decoding of the pinned G1 asset confirms blank sprite 3123 has 1,024 covered pixels, all palette index 10. Both bounded and giant CLI use the same option handling; no new CLI semantics or giant/outside camera is required to exercise the switch. This is code-backed reachability, not an executed new capture claim. A staged additive runner mode `--background-policy controlled` uses a separate version-2 fixture identity and requires nonzero index differences and index10-to0 differences for every camera pair. It preserves the original version-1 default fixture.

Actual offscreen viewport tests for hide-base/hide-vertical/underground/clip flags remain separately required: these flags can trigger the frozen index10 clear and are not exposed by screenshot CLI options. Existing synthetic offscreen alpha-policy tests do not prove those viewport branches.

No missing-scene or obviously broken scenery problem was found in the initial reference-only review. That checkpoint compared no current-software or Vulkan CLI images and accepted no exception. The completed E5 actual-caller comparison and fresh repetitions are recorded below.

The frozen receipt pins supplied assets/configuration but lacks a post-load CSG observation hook. Visual presence of the scenery is useful non-vacuity evidence; it does not replace that missing loaded-asset assertion. The executable is the receipt-qualified frozen-core CLI build with reviewed startup-path plumbing, not the originally packaged binary.
