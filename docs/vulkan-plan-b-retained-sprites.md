## Owner clarification: full redraw and direct replacement

The owner's implementation order is now explicit: first hardwire Vulkan and remove Software selection/UI, then retire the entire CPU world graphics pipeline family by family. This supersedes the earlier sequence that postponed Vulkan exclusivity until parity and performance gates closed. Removing the selectable backend does not remove the CPU painter currently feeding Vulkan. Track those remaining paths and their deletion dependencies in the [CPU rendering retirement inventory](vulkan-cpu-rendering-retirement-inventory.md). Missing Vulkan support must fail a graphical request explicitly; pure nongraphical simulation and asset decoding need not create a GPU device.

The owner explicitly rejects lazy repainting. Earlier attempts usually dirtied most of a heavy scene anyway and introduced unstable stale-chunk artifacts. Do not reintroduce dirty screen regions, cached world raster tiles, preserved background pixels, or conditional repainting as the performance strategy. Optimise for a dense, continuously changing park, not repeated identical frames.

Rewrite world rendering as a GPU-driven pipeline. Every rendered frame clears its world colour/depth targets and draws the complete current visible world from a coherent state snapshot. GPU code selects images and animation parts, computes placement, projection, visibility and ordering, and composes effects. Resident textures, immutable asset metadata and raw world-state buffers are inputs to that full redraw; no earlier rendered world pixels are an input. UI overlays compose over the freshly rendered world.

The CPU publishes simulation state and manages resource lifetime/submission. It must not visit world objects to choose sprites, construct a world draw list, assign painter order, or rebuild camera-dependent graphics. Port the old renderer's visible behaviour into new GPU logic, then delete the replaced CPU implementation and its compatibility plumbing. Use the frozen renderer externally as an oracle during development, rather than retaining an in-process CPU world painter as part of the completed architecture.

Source-state updates may use deltas to reduce transfer bandwidth, but must remain correct and efficient when the entire dynamic population changes. They must not determine which screen regions are repainted. Immutable CPU snapshot chunks are state ownership, not rendered-image chunks; retain that implementation only if it supports simple, coherent publication and measured worst-case throughput. The current foundation is not an architectural obligation.

Implement in measured stages. Keep a change only when it produces a meaningful measured improvement or a demonstrably cleaner implementation that advances this architecture; revert unsuccessful experiments. A contract or shader test alone is not a performance result. The required final result includes substantial ordinary-park performance improvement, correct mixed-scene ordering and exclusive Vulkan rendering.

The owner explicitly authorizes upstream rendering as an ordering reference, subject to its own possible bugs. In the reported scene, track/supports and tracked vehicles on tiles behind a foreground tree must not overwrite its canopy. Reproduce and inspect this case across movement and camera rotations before generalizing the rule; do not replace spatial ordering with a global object-type priority.

## Minimal graphical state contract

Implementation cadence clarified by the owner: replace obsolete representations and writable interfaces in coherent batches, migrate their callers, then use compiler errors and focused regression tests to finish the migration. Central object mutation methods own change publication; do not patch more independent notification sites around publicly writable state. Temporary compile failures during this replacement are expected. Keep durable reference artifacts intact, but do not turn each small edit into a separate investigation and validation cycle.

The owner's [object-owned runtime doctrine](C:/Users/imper/Documents/GitHub/augustus_cpp_huge/docs/object_owned_runtime_refactor.md) and its `BuildingGraphics`, `BuildingGraphicsDef`, `BuildingGraphicsState` and `Building` implementation provide the ownership model. Object methods own transitions and invariants. Shared graphical definitions are immutable and bound at object/catalog lifecycle boundaries; a composed runtime module binds its owner, definition and mutable graphical state. Creation, replacement, unload and destruction own registration/rebinding/retirement. Consumers call the object or its module, without rebuilding relationships through per-frame ID/type scans. Save records are import/export data, not the permanent runtime API. Remove replaced helpers and writable back doors rather than retaining both interfaces. Plain data needs no ceremonial accessor; methods are justified by actual transition, publication, ownership or other invariant enforcement.

Apply this ownership model to the GPU architecture, not the other project's CPU draw stages: owner-bound methods publish semantic graphical changes, shared resident definitions supply shader rules, and shaders select/compose visual parts. Cross-thread rendering owns an immutable revision and catalog lifetimes; it must not follow live mutable simulation-object references. Existing raw entity memcpy/clone paths must be removed or replaced before embedding owner references in copied runtime objects, otherwise a copy would retain bindings to the wrong owner. No borrowed CPU pointer becomes the VRAM ABI.

The owner's state-update clarification is binding: ask **which graphical facts changed**, not which objects or screen areas need repainting. A resident instance contains the minimum facts needed to reproduce its graphical instantiation. Every frame still draws the entire visible world. State residency and selective field updates reduce CPU work and transfer bandwidth; they do not preserve world pixels.

Separate instance lifecycle, rarely changing appearance, frequently changing motion, shared asset rules and global view state. Do not retransmit appearance or immutable coordinates because a position or animation phase changed. Do not copy gameplay-only state into presentation records. The publication producer reports authoritative mutations without choosing textures or preparing graphics; GPU rules derive the graphical consequences, including neighbours affected by terrain edits.

| Data class | Resident representation | Update trigger |
| --- | --- | --- |
| Terrain identity/location | Tile index implies fixed X/Y within a map epoch; shared terrain/edge catalogs hold texture groups and graphical rules. | Map creation/replacement or topology change. No per-frame X/Y copies. |
| Terrain mutable appearance/shape | Height, slope, surface/edge material, grass stage and other demonstrated graphical inputs. Grass has multiple stages; do not reduce it to a mowing boolean if that loses artwork. | Actual edits/growth/mowing/material changes. Camera motion never republishes tiles. Shared shader rules select images and components. |
| Entity motion | Stable identity/generation plus position, direction and the history needed for interpolation. | Movement/direction change; update motion independently of appearance. Retain coherent source ticks and sufficient previous/current state when rendering skips simulation publications. |
| Entity appearance | Object/archetype reference, colours, costume/accessories and only other proven graphical attributes. | Actual appearance mutation or required handle rebinding. A shared catalog change replaces catalog data without resending unchanged instance appearance. Walking alone does not upload appearance. |
| Animation | Shared resident sequence definitions; per-instance sequence/state and minimal timing or phase information. | Start/stop/transition or authoritative phase change. Predictable sequences may use start tick, rate and loop policy so shaders derive phase from the consumed presentation time. Irregular/event-driven animation publishes its actual phase; never advance independently of paused simulation or authoritative events. |
| Camera and global effects | One view/global record containing rotation, origin, zoom, presentation time and relevant global visual settings. | View/time/settings changes. These do not invalidate instance state. |
| Shared artwork/rules | Resident textures, image-group metadata, frame offsets, remaps and component definitions. | Asset load/reload or genuine dynamic asset mutation. Never upload a rendered world image or per-instance copies of shared sequences. |

Moving a peep normally changes its motion fields; advancing a known animation changes or derives a phase, not a CPU-selected image ID. Shader selection must follow the actual sequence table, including noncontiguous images, frame offsets, direction and attached parts. A simple image-group offset is sufficient only where the asset format guarantees that layout.

Sequence/state means authoritative semantic/action state or an asset-independent animation handle, not the legacy painter's resolved sprite/group. GPU rules own the state-to-visual-sequence decision. Sequence progression may follow ticks, movement or events; preserve its actual clock and rebase or stop at pause, teleport and state transitions as appropriate. Do not assume every animation advances at a constant wall-clock rate.

Use bounded dirty identities/field masks or separated buffers as an implementation choice, with deletion/reuse generations and coherent revision ownership. Coalesce the latest absolute field values and tombstones since each consumer's acknowledged revision. Skipping intermediate simulation publications is normal and must not trigger a complete upload; resynchronize complete state only when the required history/base is unavailable, or at lifecycle reset. Separate streams commit as one coherent revision/tick with owned catalog generations, so a renderer never combines new motion with stale identity, appearance or animation after a transition or slot reuse. Require a dense all-moving-population workload: update bookkeeping must remain efficient when almost every dynamic instance changes.

Batch updates into bounded transfer/scatter operations; do not issue a Vulkan submission or copy command for every changed scalar. Choose field-group alignment and encoding by measured total CPU/GPU cost rather than minimum bit count alone. A small flag change should carry only its identity and relevant field-group payload, without pulling unrelated appearance/history through the publication path.

The existing raw peep records, chunk publications and mutation notifications establish ownership and correctness groundwork only. They are **not yet** field-minimal GPU transfers, GPU-native production world rendering or a demonstrated speedup. Auxiliary custom-image invalidation is a separate asset-lifetime requirement, not a model for world repainting.

## Representation and frame

Represent the world using the existing artwork's sprite components. Retain static instance definitions and catalogs until their inputs change. Publish compact dynamic state for entities, lifecycle changes and animation. GPU stages select images, expand objects into components, calculate anchors/offsets, cull and draw batched instanced quads. Each atomic component initially uses one depth value across its opaque pixels, with defined local layer ties for attachments or coplanar art. The screen projection and pixel snapping match the current four camera rotations.

The first ordering hypothesis uses camera depth from world coordinates plus narrowly scoped layer ties. Tile and subtile coordinates are combined before projection/depth. It must be tested against existing component bounds and overlap behavior: the legacy renderer compares 3D extents and attaches children, which does not prove that an anchor-based scalar reproduces every intended ordering.

Alpha-tested holes expose the current frame's background without writing depth. A depth buffer composes opaque components; genuine translucency and destination-dependent palette effects require explicit composition in either plan. Existing legacy commands and previous world-frame pixels are not inputs. GPU stages evaluate visibility and render the full visible world every frame using resident source data. Picking maps visible components to stable simulation identities.

## Expected benefits and uncertainties

Atomic components match the structure of existing paint output and can reuse the art without constructing new surface-depth assets. Batched quads and resident catalogs keep rasterization simple. Resident state and GPU visual evaluation remove repeated CPU paint preparation.

A single depth per component may fail when component extents or grouping affect ordering. Correcting this could require additional component decomposition, bounded GPU ordering logic, or adopting depth-bearing surfaces for some families. Any such expansion must be documented rather than hidden behind broad pixel tolerances. Existing splitting into components is supporting evidence, not proof of universal scalar ordering. No particular FPS/TPS result is promised.

## Performance-led rewrite boundary — September 23 implementation review

The owner reaffirmed that substantial performance improvement is decisive and authorized deeper rewrites of the rendering pipeline. “Safer and quicker” was a reason to test Plan B, not an established outcome. Passing isolated GPU rules or reducing uploads in a tiny fixture does not validate that choice. The initial component scalar failed; a bounded geometric plane refinement fixes its obvious overlap errors but still has unresolved exact contact pixels. See the [manual review](vulkan-plan-b-plane-visual-review.md).

The next production milestone must remove the **complete CPU world-preparation pass**. The existing complete-scene return in `ViewportPaint` already provides the boundary: after submitting an admitted retained scene, skip `CreatePreparedViewportFrame`, column tile/entity traversal, `PaintSessionGenerate`, `PaintSessionArrange` and world sprite-command recording. UI composition remains separate. The current ordinary-park baseline spends about 27 ms of CPU time per draw; a peep-only selector does not remove most of that work.

Implement this as one coherent replacement, not another bridge between CPU painter ordinals and GPU depth:

1. Publish coherent raw map/entity state and stable identities. Load immutable artwork, metadata and GPU rule tables at asset boundaries. World-dependent component/image decisions belong to GPU code. Do not retain `PaintStruct` lists or run the world painter to generate a frame stream.
2. Give GPU rules the raw neighbouring state needed for terrain edges, connected paths, supports and tunnels. Avoid a CPU graphics-invalidation graph that reconstructs the old painter through caches. Object/ride edits update authoritative state and asset generations.
3. Publish raw peep and vehicle state with interpolation history and authoritative appearance changes. Eliminate the admitted families' legacy snapshot copies and CPU spatial-index construction.
4. Select/expand components, cull and resolve static/dynamic ordering in the GPU, then redraw the complete visible world. Use scalable parallel compaction; the finite diagnostic's serial 1,024-slot loop is not a production implementation. Camera motion updates camera state and triggers a full GPU redraw without CPU sprite preparation.
5. Maintain whole-scene capability from published revisions. Admission requires all visible families/effects, current resident asset generations, supported view modes and retained light emitters. Do not silently leave expensive CPU preparation active while describing the path as GPU rendering.
6. Benchmark the same operating park, camera and simulation work at actual 4K for at least 3,000 measured ticks. Compare CPU preparation, publication, transfers, GPU time and TPS; separately inspect actual displayed pacing. Revert an unsuccessful implementation unless it demonstrably simplifies this replacement boundary.

Terrain, ordinary paths, simple scenery, peeps and balloons can establish a restricted-scene scaling experiment. They cannot establish the requested operating-park improvement. That requires track/support/tunnel recipes and vehicles, then the remaining world families. “Static” recipes must keep animation clocks, scenery age, signs, ride colours/station state and path additions as changing inputs. LightFX, water, glass and destination-dependent palette operations need explicit rendering support before their CPU painters disappear.

The raw publication foundation is retained for its cleaner ownership boundary and concrete lifecycle fixes. Its default-off state is not a performance result. Further fixture expansion alone is not the next milestone; the decisive work is the complete retained world pass and its measured removal of CPU preparation. If implementing generic component ordering becomes more complex or slower than depth-bearing geometry, compare that cost directly with Plan A instead of protecting the original recommendation.
