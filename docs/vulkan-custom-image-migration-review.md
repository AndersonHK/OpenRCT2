# Custom-image migration: behavior review and open gates

This review compares the custom-image migration with `git show ba5b9d8a92a3ae6ca98c570c7d23f6114c2a470e:src/openrct2-ui/scripting/CustomImages.cpp` and its software bitmap blitter. The migration removes X8 from `JSDrawCustomImage` and records through the Context's shared Vulkan service. [Build75](../obj/vulkan-parity/build-75/receipt.json) passes with zero warnings/errors; [run57](../obj/vulkan-parity/run-57/summary.json) passes 855/855 production tests, including all 66 parity cases, with clean validation and unchanged pinned inputs. The corrected nested-image test passes all downstream checks. The subsequent bounded ordered GPU alias implementation and its artifact exporter compile in [build77](../obj/vulkan-parity/build-77/receipt.json) with zero warnings/errors. [Build79/run60](vulkan-state-ownership-checkpoint.md) now pass 867/867 tests, including 66 parity cases, with clean validation. All fifteen alias samples are exact and [manually reviewed](vulkan-custom-image-alias-visual-review.md); run58, run59 and run60 alias reports are byte-identical. Earlier overall failed receipts remain failed. Large-image support remains unimplemented. This is not universal callback parity or deployment qualification.

## Observed stale-atlas failure and correction

[Run55](../obj/vulkan-parity/run-55/tests.log) finishes with 848/852 production tests passing. The custom-image failure is `CustomImageCallbacksResumeNestedTargetsAndExposeCurrentIndices`; the other three failures are track-preview tests outside this review's scope. The nested callback fails its expected B pixels `[11,2,4,12]`, then its completion assertion. The old diagnostic did not print the actual pixels; the corrected assertions identify each stage and include actual arrays/flags. This failed receipt remains failed.

Source diagnosis identifies a missing invalidation route: a preceding self-image draw cached A in the offscreen service, then an intermediate outer-context draw changed A's pixels. `DrawingEngineInvalidateImage` notified only the display engine, leaving the service's persistent source atlas stale when the inner callback drew A into B.

The correction routes existing `DrawingEngineInvalidateImage` notifications through the Context to an already-created shared render service as well as the display engine. Lazy-owner notification is synchronized with service publication/shutdown and never creates a service or device. Vulkan producers coalesce image IDs under a mutex; the owner thread drains them before beginning a recording and when acquiring its target/drawing context. Cache invalidation retains allocations already bound by a recording until their existing retirement rules permit release. Custom-image free/reset now emits the same notification as upload/publication. This is shared auxiliary cache coherence, not a custom-only cache bypass or a per-frame asset scan.

Run56 passes the worker-thread freshness and track-preview tests. Its nested callback reports B pixels `[11,10,4,12]`, so the changed outer pixel 12 is now visible. The remaining expectation of index 2 was incorrect: the unchanged old `GraphicsContext.image` binding always calls `WithTertiary(0)`, even without explicit colours. The first self-image draw maps reserved glyph indices 2/3 to 244/245 through the legacy tertiary table, and the second image draw maps 244 through the loaded black palette to 10. The corrected test asserts both the first transformation and the loaded palette entry, rather than changing production remapping or waiving pixels. Later RLE/native-failure and empty-clip checks were not reached in run56. Build75 changes the test expectations only; the focused nested callback run and full run57 now pass all those checks. This does not cover the translated overlap and large-image gaps below.

## Historical overlapping self-blit divergence and applied correction

The old same-size raw path assigns `rt.bits` directly to the source sprite's `offset`. [`DrawBMPSpriteMinify`](../src/openrct2/drawing/Drawing.Sprite.BMP.cpp) traverses rows top to bottom and each row left to right; [`BlitPixel`](../src/openrct2/drawing/Drawing.Sprite.h) reads each source pixel at the time it writes its destination. Therefore a translated overlapping self-blit reads pixels already overwritten by earlier iterations. The initial Vulkan migration first materialised the source and uploaded an immutable sprite snapshot.

For a 4×1 raw image `[20,21,22,23]`, drawing that image onto itself at `(1,0)` produces:

| Path | Result |
| --- | --- |
| Prior software, forward in-place traversal | `[20,20,20,20]` |
| Initial Vulkan migration, source snapshot | `[20,20,21,22]` |

These ordinary indices avoid reserved glyph/remap ranges. Both old and new script bindings apply the same default three-colour remap through `WithTertiary(0)`; using indices 1–3 in this example would additionally remap the source and obscure the aliasing difference.

This is a real behavior difference, not a tolerance or readback artefact. A same-position self-blit test does not cover it. Forward overlap also crosses rows when translated downward; clipping and sprite offsets change which source/destination pixels alias.

Transparency and remapping are part of the recurrence. With `hasTransparency`, source index zero skips a write; a preceding write can replace that zero before it is read. Source-remap operations may repeatedly remap values propagated by earlier iterations; destination blending must use the destination value at that point in the scan. Unremapped raw images without the transparency flag copy zero rather than skipping it. The script binding always applies `WithTertiary`, so its reachable image draws use the source-remap branch, which skips source and mapped zero even when the raw transparency flag is absent. RLE conversion and resized draws have separate temporary destinations in the old code, so they do not have this source/target alias recurrence.

The type declarations describe drawing directly into an image and retaining its pixels between calls, but do not specify overlapping self-copy semantics. The propagation looks like an implementation side effect of shared storage and scan order, rather than an explicit image-copy contract. That observation is insufficient to waive the difference: plugins can observe or rely on it.

The chosen correction preserves the original scan order; snapshot behavior has not been accepted as a waiver. `CustomImageDrawing::DrawOrderedAlias` now intercepts translated overlapping same-ID, same-size raw copies, computes the clipped source/destination rectangle using the original sprite offsets and signed-16-bit placement, and copies the existing legacy remap table. It flushes preceding commands, submits an exclusive owned `OrderedImageAlias` request through the configured shared service, publishes completed indices using ordinary image invalidation, and resumes recording lazily. Resized/RLE, disjoint and identical-position copies retain their existing separate-source path.

`VulkanImageAliasPipeline` uses a mutable packed-uint storage buffer on the existing shared device and submission slot. One invocation scans at most 8192 pixels per dispatch; storage barriers preserve recurrence between slices. At the existing 4,194,304-pixel target cap this permits at most 512 dispatches. Source reads occur immediately before destination writes, preserving propagated remaps and zero skips. The owned request validates both rectangles and forbids additional drawing commands, scaling, RGBA output and lighting. Existing fence retirement retains descriptors/uploads until completion. No CPU raster fallback, extra device or world draw-stream command is introduced. Arbitrary destination blending is not exposed by this script binding and is not claimed by this narrow operation.

Build77 compiles the implementation and three focused regressions: invalid request geometry/output contracts; actual submitted ownership, cancellation and zero policies; and script callbacks covering both axes/directions, diagonal recurrence, transparency, remapping, clipping, sprite offsets, nested recorder switches and multiple scan slices. The script test optionally exports 15 cases under `samples/custom-image-alias/report.json` with seed, explicit legacy expected, immediate and final indices plus the real palette. The existing runner hashes that report. These expectations are original scan-order fixtures, not a new software execution. All three regressions pass in run60, and all fifteen saved cases pass manual inspection. This qualifies the finite bounded alias corpus; neither large images nor the maximum-capacity workload is covered.

## Image-size limits

The old `ImageManager.draw` binding did not impose a pixel-count cap. Positive dimensions representable by the signed 16-bit sprite metadata, such as 3000×2000, could be drawn by the software target. The configured Vulkan service currently limits a target to 4,194,304 pixels. Individual device extents and the 2048×2048 source-sprite atlas impose additional constraints.

The initial migration allocated the complete seed, then copied it into `BeginOffscreen`, before the service rejected oversized targets. At 32767×32767 this could allocate roughly two GiB of CPU buffers for an operation known to be unsupported. The follow-up checks the matching 4M-pixel limit before seed allocation; a regression verifies that a 3000×2000 request fails before callback/service execution. This fixes wasteful failure handling but **does not restore large-image API coverage**. The size regression remains open; there is no deployment or broad custom-image completion claim.

Restoring larger targets requires a capability-aware session or bounded tiled execution of a single recorded callback. Replaying the JavaScript callback once per tile is invalid: callbacks can allocate images, mutate other images and read intermediate pixels. Merely increasing the service limit also does not cover device extent or source-atlas limits. A new public image-size restriction would instead require an explicit compatibility decision.

The [bounded segment execution proposal](vulkan-large-custom-image-design.md) specifies destination tiles, immutable source pages and command-order groups under the existing synchronous callback boundaries. It remains unimplemented. It must preserve one callback execution and atomic segment publication while keeping atlas/upload residency bounded; it does not solve overlapping self-copy by snapshotting it.

## Failure and lifetime behavior

The latest correction gives custom graphics contexts a native-recording failure hook. A native drawing exception cancels that recording and retains its first exception; `Finish` rethrows even when JavaScript catches the inner graphics error. The callback test forces an actual oversized source-atlas failure after a valid command, checks that the partial command is not committed, and retries a valid draw on the same service. This addresses the initial defect where the native error was logged by `ExecutePluginCall` and a partial recording could then be committed as success. User-authored JavaScript exceptions retain the established log-and-commit-preceding-drawing behavior. These tests pass in run57, including cancellation and valid retry on the same service.

Submission and wait errors propagate. Each complete result must match the submission identity, dimensions, palette and requested indexed payload before publication. Same-size raw intermediate reads intentionally publish completed segments, so a later failure retains the last successfully published segment rather than rolling the whole callback back. Resized/RLE destinations remain private until final publication. A timeout does not reclaim submitted job resources; the service owns its leases until retirement and rejects reuse while busy.

Nested other-image draws and same-size raw same-image draws switch the single shared recorder by submitting/waiting and resuming from owned indices. Callback-local clipping is rebound when the target changes, including when an inner callback uses the outer graphics context. Escaped graphics objects cannot draw after callback completion. Freeing, replacing, resizing or converting an active destination is rejected explicitly because those operations invalidate its borrowed target; allocating/uploading/freeing other images remains supported. Tests cover these paths, but this source review does not establish universal callback parity or a performance improvement.

The empty-clip correction computes intersections with checked 64-bit geometry before moving pixel pointers. The previous generic helper could form an out-of-allocation pointer before reporting an empty intersection, which the binding ignored and `Flush` later subtracted. Empty clips now have canonical zero extents and all drawing operations return before recording or resolving source sprites; flush/resume keeps a safe offset. The authored regression covers eight outside, zero, negative and extreme-coordinate clips through pixel reads and nested callback switches, including drawing a source too wide for the atlas to prove that an empty image draw never resolves it. Existing nonempty nested clipping retains local coordinates. These checks pass in run57. The overlapping-copy corpus passes run60 and manual visual qualification; large-image support remains a separate unimplemented gate.
