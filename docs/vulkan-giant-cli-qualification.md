# Giant CLI qualification checkpoint

This additive diagnostic checkpoint is staged, uncompiled and unexecuted. It does not mark giant screenshot migration complete. Existing regular screenshot modes and receipts remain version 1/2; opt-in `OPENRCT2_CLI_GIANT_PARITY=1` produces a separate `screenshot-cli-giant` version 1 report. The new runner writes schema 3 `giant-cli-parity` receipts. The configured factory and verified frozen-data/SPIR-V overlay helpers remain the same production lane.

The frozen software core remains unchanged. A separate `GiantScreenshotFixtureMain.cpp` prepares only when compiled with the frozen-only preparation define; its current-core build can only reload and inspect. The 96×96 recipe has 9,216 exact surface elements, two surfaces/two edge objects, all ordinary slope variants, mixed grass, water, four 512-unit corner elevations, and 800 legitimate remapped balloons in overlapping pairs. Neither preparation nor reload advances ticks. Census compares raw tile bytes, loaded object identifiers/sources, every balloon record, entity/spatial populations, weather, random state and camera. Both frozen reloads and the current reload must equal the export census byte-for-byte after canonicalisation.

Independent scalar derivation from the pinned frozen giant viewport algorithm predicts 6016×3488 at zoom 0 for each rotation, hence a 3×2 tile grid with a 1920×1440 final tile. Zoom 1 is 3008×1744 (two horizontal tiles); zoom 2/3 controls are 1504×872 and 752×436. These are predictions until actual export/reload and PNG checks pass. This source-only fixture contains no rides or tall scenery; the raised surface bounds exercise giant top extent while paired balloon sprites exercise overlap/remapping. Do not claim tall scenery/ride coverage from this fixture.

Each completed tile records its own indexed buffer, palette, submission/target generation, request extents and paused ticks. Session begin records prove prior completion and underlying session retirement; the final report requires one peak session, none remaining, one service and persistent configured owner device state. Tile offsets are **inferred from the pinned row-major core protocol**, since the approved session request carries name/extents but no output offset. Every inferred tile row must equal the final PNG bytes. This is an independent check of assembly against owned outputs, combined with a whole-image frozen oracle comparison. GPU RGBA readback is deliberately absent for giant exports; decoded PNG RGBA is compared independently with frozen PNG RGBA, alongside all indices, palette RGB and the full tRNS alpha table.

The runner executes 20 fresh processes per lane: ordinary/transparent × rotations 0–3 at zoom 0/1, plus rotation 0 zoom 2/3 controls. It pins receipts, original source/installed asset trees, executable/libraries, runtime DLL membership, shaders, helper and runner before/after. Each case has a bounded timeout, strict Vulkan validation activation and generic warning/error detection, and retains failures/partial artifacts. Source asset roots must exactly match the accepted fixture. A fresh-repeat lane must use the same executable, libraries, shader identities and inputs. Current software requires the successful frozen fresh repeat; Vulkan requires both frozen and current software fresh repeats.

PNG dimensions are directly observed. Camera coordinates derive from the unchanged frozen algorithm and exact census, since original CLI has no camera hook. Loaded CSG/G1 are directly observed only in the Vulkan factory lane; the independent fixture census does not prove those same assets loaded in each factory-free software CLI process. Device observation is the configured owner's persistent created state, not interception of Vulkan API calls.
