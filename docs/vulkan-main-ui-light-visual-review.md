Fixture version 1 did not establish deterministic lighting input. Agent `decode_assets` manually viewed all four physical reference/candidate/amplified-difference triplets, then all four three-times enlarged entrance-area triplets with a 64-times difference amplification. The samples have identical geometry and light placement; differences are tiny red-channel changes on lit entrance surfaces/sign pixels, not moved sprites or changed occlusion silhouettes. SHA-256 receipts for original images are in [vulkan-main-ui-light-repeat-review.json](vulkan-main-ui-light-repeat-review.json). The palette metadata identifies the unstable state: paint 3 has the same dark palette hash (11691001366976653668), but differing light palette hashes (15586725313504401240 versus 2590828009337670855). `LightFX.cpp` has no random/flicker/time call in this path. `Context::SetProgress` instead uses a wall-clock update throttle and can call `Draw()` while loading the park. These uncounted progress paints call `UpdatePaletteEffects`. With lighting enabled, `ApplyPaletteFilter` advances function-static fog/wetness/light-pollution adaptation. Setting fixed weather and night only after loading cannot undo that variable startup history.

Version 2 normalizes the controlled input through existing public behavior: lighting remains disabled through context initialization and park loading, then is enabled after loading; the selected actual engine receives a same-size resize so its light buffers are available. The harness pins night/weather and performs one full palette refresh, then exactly two warmup paints and the four named captures `light-paint-3`, `light-paint-4`, `light-paint-5`, `light-paint-6`. Private adaptation state is not reset and frozen renderer source is untouched. The initialization event sequence is explicit in each report's `lighting.initialization`; only the light-night fixture version is bumped.

This qualifies controlled off-to-on activation followed by natural main-UI lighting. It does not qualify arbitrary startup-enabled progress histories. Every renderer must be run in separate fresh processes twice, comparing corresponding named ordinals and the complete `lighting` metadata object. Adjacent paints are deliberately not required to match. Vulkan must show nonempty resolved commands, no CPU intensity attachment, and an enabled successful physical output; its backend throws if a command-only packet cannot run through GPU accumulation. Version 2 is now qualified for the bounded sequence below; startup-enabled lighting remains open.


## Version 2 corrected result

Current UI build 11 and frozen UI build 09 produced six passing process runs: `ui-frozen-light-night-03/04`, `ui-current-light-night-03/04`, and `ui-vulkan-light-night-03/04`. Each `04` is a separate fresh-process repeat of its corresponding `03` with the same renderer build. Current/Vulkan `03` match frozen `03`. All four matching ordinals have zero indexed and physical RGBA differences, identical complete lighting input metadata, and clean Vulkan validation. Agent `decode_assets` independently compared all 24 captured frames byte-for-byte against the corresponding frozen `03` frames, including the complete `lighting` metadata object.

The agent manually opened reference/candidate/diff physical triplets for all four ordinals in the corrected Vulkan-versus-frozen comparison and all four ordinals in the frozen fresh-process repeat (24 PNGs). The park entrances have matching bright illumination against the dark park, including the tiny red-component details that failed version 1; geometry, shadows and surrounding night colours match, and every viewed difference image is black. The review and SHA-256 receipts for manually viewed images, all six run summaries and all 24 raw frame pairs are in [vulkan-main-ui-light-v2-review.json](vulkan-main-ui-light-v2-review.json).

Every Vulkan capture resolves **six natural lights**: two lantern2 and four lantern3. The packet has no CPU intensity attachment and the successfully captured output has LightFX enabled. This proves the command-only GPU accumulation route for these actual main-UI frames: the backend rejects a command-only packet if it cannot execute GPU accumulation. The fixture has no injected light sources.

All four ordinals and all six processes share dark palette FNV-1a-64 `1243344898264867578` and light palette FNV-1a-64 `4573124237079475475` (native `GamePalette` byte order). The Vulkan packet's RGBA-ordered light palette hash is `4828772568644702067`; these differently ordered palette hashes are not compared to each other. Resolved-command hash is `2836593439978595784` at paint 3 and `6483248878311902136` at paints 4–6. The latter illustrates why command temporal history is recorded per ordinal even when captured image bytes happen to remain equal.

The bounded closure is recorded as `LIGHT-001-startup-palette-history` in the visual-review ledger, with no new accepted exception. Coverage remains one fixed small park, tick 1215, rotation 0, zoom 0, 960×640, night 1, sunny 20°C, full invalidation, vehicle lights disabled and controlled off-to-on activation. **Lighting enabled throughout startup remains an explicit temporal gap**: arbitrary loading-progress histories are not normalized by production changes, not accepted as divergent pixels, and not covered by this passing sequence. Other rotations/zooms, weather and palette transitions, source linger/removal, resize, vehicle/shop/staff families and additional occlusion layouts still need independent fixtures.
